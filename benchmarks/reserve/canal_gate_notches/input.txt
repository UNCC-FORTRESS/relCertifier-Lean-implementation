# canal_gate_notches: an irrigation-canal pool under an automatic three-position gate controller,
# against the canal's manual operating rule, which permits four gate notches and restricts the
# two extreme ones by level; the reference must commit to a nearby permitted notch.
# scenario: controller-refinement
# mechanisms: X (committed existential choice: at each window start the reference hops into a
#   permitted notch that is NOT the deployed's position, RELCERT_NO_CHOICE=1 declines)
#
# Round A (2026-10-26): the previous file certified under ANY deployed switching schedule (every
# deployed position had a near notch permitted at every level). The deployed now opens the gate
# to near-full and near-minimum positions, whose only near notches are the extreme ones the rule
# restricts by level, so the claim depends on where the automatic controller uses them.
#
# System. Water level h in m above the downstream check crest, time in min. One canal pool, 2 km x
# 10 m (surface 20 000 m2), fed through the upstream sluice gate (inflow Q, m3/s) and drained over the
# downstream check structure, outflow linearized to 2 h m3/s; so h' = (Q - 2 h) / 20 000 per s, i.e.
# h' = 0.006 (Q/2 - h) per min (time constant 167 min): each gate setting holds the pool at Q/2.
# Decisions every 10 min on both sides (the SCADA polling cycle), lambda fixed to 1.
#
# Right (reference): the manual operating rule. The gate has four notches, inflow 2.0 / 1.5 / 1.0 /
# 0.5 m3/s (N100 / N75 / N50 / N25, holding 1.0 / 0.75 / 0.5 / 0.25 m). The rule restricts only the
# extremes: N100 only below 0.6 m (it fills toward 1.0 m, close to the 1.2 m bank), N25 only from
# 0.7 m (it would starve the turnouts at low level); N75 and N50 are permitted at every level; any
# notch may follow any.
# Left (deployed): a motorized gate with an automatic three-position controller around the 0.65 m
# operating level with a +-0.25 m deadband: RAISE (h < 0.40, gate at 95 %, inflow 1.9, holds
# 0.95 m), HOLD (0.40 <= h < 0.90, inflow 1.3, holds 0.65 m), LOWER (h >= 0.90, gate at 30 %,
# inflow 0.6, holds 0.30 m). One cause: the deployed resolves the rule with its own positions,
# none of which is a notch (a refinement).
#
# Property (every left mode): |h_L - h_R| <= 0.15 m. Requirement: the canal operator's level
# tolerance for the pool, +-0.15 m (at the turnouts' 1.5 m head this keeps each delivery within
# about 5 % of its order). Every deployed run stays within 0.15 m of a run the rule permits.
# Tightest 0.10 (0.09 declines): HOLD's 0.65 m is 0.10 m from N75's 0.75 m; RAISE's 0.95 m is
# 0.05 m from N100's 1.0 m and LOWER's 0.30 m 0.05 m from N25's 0.25 m, but at 0.15 m those two
# have no other near notch (N75 is 0.20 m from RAISE, N50 0.20 m from LOWER). With the positions on
# the notches (1.0 / 0.75 / 0.25) the exact claim (0 m) CERTIFIES (NO_CHOICE declines). Not
# implied by the domains; certifies for every tolerance from 0.10 m up (0.2, 0.3, 0.6 checked).
#
# Cause dependence (the controller's switching law, measured at 0.15 m):
#   an arbitrary left schedule (every left mode on the whole range [0, 1.2], every mode a successor
#     of every other): DECLINED; it needs 0.20 m (0.19 declines): RAISE above 0.45 m relates to a
#     reference at or above 0.6 m, where N100 is not permitted, and LOWER below 0.85 m to one below
#     0.7 m, where N25 is not;
#   law window: the RAISE threshold must stay at or below 0.6 - 0.15 = 0.45 m and the LOWER
#     threshold at or above 0.7 + 0.15 = 0.85 m (thresholds 0.46 and 0.84 DECLINE, measured on the
#     +-0.2 m variant); the file's 0.40 / 0.90 keep 5 cm;
#   rule dependence: with N100 and N25 permitted at every level, the arbitrary schedule CERTIFIES
#     at 0.15 m: the law matters because the rule restricts the extreme notches.
#
# Why committed choice is needed (X), and why it is not the identity hop. At a window start the
# reference may be at any permitted notch within 0.15 m of the deployed level. With the choice it
# switches at once (zero-duration hop) into the notch that tracks the deployed position: N75, N50
# -> N100 for RAISE; N100, N25 -> {N75, N50} for HOLD; N75, N50 -> N25 for LOWER. The hop target is
# never the deployed's own mode (the deployed has no notch modes). Without the choice the
# reference must flow on in the wrong notch: RELCERT_NO_CHOICE=1 DECLINES (also at 0.2, 0.3 and
# 0.6 m).
#
# Domains. 0 <= h <= 1.2 m on both sides: empty pool to the bank crest, forward invariant at every
# setting (all hold levels lie in [0.25, 1.0]). The right guards cover [0, 1.2] (N75 and N50
# everywhere); the left guards partition it; every left mode has a satisfiable start (h_R = h_L in
# N100 for RAISE, N75 for HOLD, N25 for LOWER). Successor sets: RAISE rises at most 0.06 m per
# poll (to HOLD), LOWER falls at most 0.06 m (to HOLD); HOLD's flow stays in its band, its declared
# successors RAISE, HOLD, LOWER over-approximate it.
#
# Verdicts (RELCERT_IMPLIED_CUT=1 unless stated, measured 2026-10-26 with the round-A binary):
# CERTIFIED (about 0.4 s); CERTIFIED under RELCERT_SYNC=1, RELCERT_NO_PRUNE=1, RELCERT_NO_CUT=1,
# RELCERT_NO_IMPLIED_CUT=1, RELCERT_NO_LINEAR_CUT=1, RELCERT_NO_PAIR_STRETCH=1, without
# RELCERT_IMPLIED_CUT, RELCERT_WELLFORMED_STRICT=1 and RELCERT_OPREGION=1 (every admitted start in
# some right guard); DECLINED under RELCERT_NO_CHOICE=1, RELCERT_NO_PRUNE=1 RELCERT_NO_CHOICE=1 and
# RELCERT_SYNC=1 RELCERT_NO_CHOICE=1. Cover: every left mode at lambda 1, budget 1, joint segment
# after at most one hop; admissible RAISE_L [N100, N75, N50], HOLD_L [N100, N75, N50, N25],
# LOWER_L [N75, N50, N25]. Nothing pruned. Rows identical (--handoff vacuous, 7/7). relcert
# --wellformed: N100 ok (exit->N50), N75 ok (invariant), N50 ok (invariant), N25 ok (exit->N50),
# 0 UNKNOWN.
