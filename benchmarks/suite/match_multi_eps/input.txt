# match_multi_eps: multiple-cycle matching via eps ratio (the eps-driven member of the
# multi-cycle-matching family). The right runs N cycles to cover one left residence because
# eps_L > eps_R; with lambda = 1 (both sides share the same dynamical rate), each sync covers
# delta_L = eps_R / 1 = eps_R, and N = ceil(eps_L / eps_R) = ceil(1.0 / 0.3) = 4. The "4
# cycles" is a budget/unit choice, not a dynamical fact: the left and right move at identical
# rates (ACCEL gain 2 shared, COAST gains 1.5 vs 2.0 -- a sluggish brake degradation where the
# deployed overspeeds and leads). Contrast with match_multi_rate, where N is forced by the rate
# ratio (lambda = k, eps_L = eps_R).
#
# Story: the deployed onboard controller has a SLUGGISH COAST brake (weak gain 1.5 vs ground 2.0)
# so it overspeeds and rides ahead of the ground model. Safety: speed envelope v_L <= v_R + 0.5.
[problem]
name = match_multi_eps
max_depth = 8
lambda_min = 1.0
lambda_max = 6.0
bound_T = 2.0
[Lsys]
state_vars = [v, s]
epsilon = 1.0
[Lsys.mode.ACCEL]
ode = v' = smt2:(* 2 (- 1.0 v)); s' = v;
guard = v >= 0.3 and v < 1.0
evolve = v >= 0.0 and v <= 1.0 and s >= 0.0 and s <= 100.0
next = [COAST, ACCEL]
[Lsys.mode.COAST]
ode = v' = smt2:(* 1.5 (- 0.2 v)); s' = v;
guard = v >= 1.0
evolve = v >= 0.0 and v <= 1.5 and s >= 0.0 and s <= 100.0
next = [ACCEL, COAST]
[Rsys]
state_vars = [v, s]
epsilon = 0.3
[Rsys.mode.ACCEL]
ode = v' = smt2:(* 2 (- 1.0 v)); s' = v;
guard = v >= 0.3 and v < 0.6
evolve = v >= 0.0 and v <= 2.0 and s >= 0.0 and s <= 100.0
next = [COAST, ACCEL]
[Rsys.mode.COAST]
ode = v' = smt2:(* 2 (- 0.2 v)); s' = v;
guard = v >= 0.6
evolve = v >= 0.0 and v <= 2.0 and s >= 0.0 and s <= 100.0
next = [ACCEL, COAST]
[relational_invariant]
ACCEL = v[l] <= v[r] + 0.5
COAST = v[l] <= v[r] + 0.5
