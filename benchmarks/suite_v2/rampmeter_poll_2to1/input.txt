# rampmeter_poll_2to1: a freeway on-ramp meter whose traffic-responsive rate table is executed on
# bottleneck-detector data that arrive every 40 s (central polling by the traffic management centre)
# instead of the 20 s local update the table was designed for, against the same table updated every
# 20 s; the claim bounds the bottleneck density gap between the two.
# scenario: degraded-network
# mechanisms: M B (multi-cycle matching, one 40 s deployed update against two 20 s design updates,
#   matrix code M2; state-dependent branching: at the joint step the design meter may step its rate
#   up or down, depending on the density band it has reached, and the cover certifies both, matrix
#   code M3)
# Suite status: back from benchmarks/reserve/ on 2026-10-29 in place of insulin_basal_cgmloss (same
#   chain-depth template and letters, M B), with the requirement re-derived from the HCM level-of-service
#   bands (8, was 10): it sits 3.0 below the 11 at which any deployed schedule certifies.
#
# System (both sides). Two-lane freeway, free-flow speed 60 mi/h, free-flow branch of the cell
# transmission model (Daganzo 1994), densities in veh/mi/ln, time in s. State: kd = the arrival
# density of the upstream demand (demand / 120: 120 = 2 lanes x 60 mi/h), constant over the event,
# kd in [10, 27.5] (1200 to 3300 veh/h); k1 = density of the 0.83-mile section upstream of the ramp
# (travel time 50 s), k1' = (kd - k1) / 50; k = density of the 1.67-mile bottleneck section
# downstream of the ramp merge (travel time 100 s), fed by the upstream section and the metered ramp
# flow r: k' = (k1 + r / 120 - k) / 100. Dual-lane meter, one vehicle per green per lane, rates from
# 2 x 240 to 2 x 900 veh/h (the FHWA default per-lane minimum and maximum metering rates, FHWA-HOP-
# 13-042, Appendix I), in the one-car-per-green cycle steps 15, 10, 7.5, 6, 5, 4 s: r in {480, 720,
# 960, 1200, 1440, 1800} veh/h, i.e. r / 120 in {4, 6, 8, 10, 12, 15}. The rate table (local
# traffic-responsive metering, the same on both sides) selects the rate from the bottleneck density
# band: R1800 below 19, R1440 [19, 24), R1200 [24, 29), R960 [29, 34), R720 [34, 39), R480 from 39.
# Regulation: a denser bottleneck gets a lower ramp rate, so the bands are left in both directions.
#   Right (design): the table updated every 20 s (epsilon 20). Declared successors: the levels the
#     density can reach within one 20 s update: the adjacent levels, and two levels from the two end
#     bands (where the density moves fastest, up to 0.285 veh/mi/ln per s); relcert --wellformed
#     proves every list (every mode ok (exit), rate bounds over the mode's kept facts).
#   Left (deployed): the same table, the same freeway and ramp, but its detector data come every 40 s,
#     so each rate is held for up to 40 s (epsilon 40); every level is a declared successor.
# The update interval is the only difference. Field controllers update every 20 to 60 s (ALINEA field
# tests used 40 s and 60 s control intervals, Papageorgiou et al.); 40 s is inside that practice. The
# averaging over the polling interval is not modeled (the deployed decides on the density at the poll).
#
# Property (every left mode): kd_L = kd_R, k1_L = k1_R (two inequalities each: the same arriving
# traffic), |k_L - k_R| <= 8 veh/mi/ln. Requirement: HCM 6th edition, Exhibit 12-15 (basic freeway
# segments), level-of-service density thresholds 11 / 18 / 26 / 35 / 45 pc/mi/ln (A/B, B/C, C/D, D/E,
# E/F; 45 is the capacity density). Inside the domain k in [14, 42.5] the bands that a gap can skip
# whole are C (width 8) and D (width 9); a gap of at most 8 cannot jump over a whole band, so the
# deployed meter runs the bottleneck at most one level of service worse than the design (the design
# table holds the bottleneck at or below 35 in steady operation for every demand in range: simulated
# steady maxima 22.0 / 25.0 / 29.1 / 33.0 / 34.3 at 1200 / 1800 / 2400 / 3000 / 3300 veh/h). The lower
# side uses the same 8 (the requirement is symmetric: the deployed must not be two levels better
# either, a sign of a wrong rate). Not implied by the domains (they allow a gap of 28.5).
# Tightest (symmetric constant c, swept at 0.01 around every jump; measured 2026-10-30): the
# certifying set is not an interval but {5.00} and [7.00, ...): 4.99 declines, 5.00 certifies, 5.01
# to 6.99 decline, 7.00 certifies. Tightest 5.00 (4.99 declines); the requirement 8 lies in the upper
# branch, whose lowest point is 7.00 (6.99 declines). Why the set has a gap: the constant c sets two
# things at once. As a start relation, the closed row |k_L - k_R| <= c over the half-open 5-wide bands
# admits design levels at most ceil(c / 5) bands away (adjacent only for c <= 5, two bands for c in
# (5, 10]); and a joint segment of two levels i, j keeps |k_L - k_R| <= |r_i - r_j| / 120 (the gap
# relaxes to the rate difference), so the one extra design update inside a held 40 s window, which
# steps the reference one level further, needs c at least the largest rate gap of levels one band
# further apart: two levels (1800 - 1200) / 120 = 5 for c <= 5, three levels (1800 - 960) / 120 = 7
# for c in (5, 10]. Hence c = 5 is a fixed point (adjacent starts need exactly 5) and (5, 7) fails.
#
# How the bound depends on the cause (measured 2026-10-30, certifying set of the symmetric constant
# against the deployed update interval, everything else fixed, swept at 0.01 around every jump; the
# same fixed-point structure: ceil(c / 5) start bands plus u extra design updates per held window):
# 20 s (no cause, u = 0): {0} and [3.00, ...) (0.01 to 2.99 decline: one level apart needs the
# adjacent rate gap 3); 30 s and 40 s (this file, u = 1): {5.00} and [7.00, ...); 50 s and 60 s
# (u = 2): [9.00, 10.00] and [11.00, ...) (8.99 and 10.01 to 10.99 decline: two start bands need
# four levels, 9; three need five, 11); 80 s (u = 3): [11.00, ...) = (1800 - 480) / 120, the whole
# ramp authority, which is also what an arbitrary deployed schedule needs (every left guard the
# domain; 5.00, 7.00, 9.00, 10.00 and 10.99 decline there too): the requirement 8 holds up to 40 s
# polling and fails from 50 s, well before the deployed is no better than an arbitrary metering
# schedule (80 s). Law dependence: an arbitrary deployed schedule DECLINES at 8 (needs 11.00). The
# design table's rate limit is load-bearing: a design reference that may jump to any level at an
# update (all levels declared) needs 11.00 at 40 s.
# Simulated (0.5 s steps, 3000 random starts and polling phases): the worst sampled gap is 1.00
# veh/mi/ln at 40 s, 1.53 at 60 s and 2.18 at 80 s; the certificate is an inductive envelope (the
# held-level spread as if it persisted), about seven times the transient, and it moves with the
# update interval as the transient does.
# Start-only levels (disclosed): R1800 (k < 19) and R480 (k >= 39) are entered only from starts (the
# R1440 equilibrium k1 + 12 >= 22, the R720 equilibrium <= 33.5); removing both (four levels) still
# CERTIFIES with letters M B (measured 2026-10-29), so neither letter rests on them.
#
# Relation to tank_dos_3to1 (the suite's chain-depth M). The bound is again a chain depth (how many
# design decisions fit in one held deployed decision), but the structure differs: there the stages
# follow an exogenous, monotone demand ramp shared by both sides, the start pairing is exact and the
# rows are one-sided; here the table regulates the very density it reads (a denser bottleneck gets
# less ramp flow), the levels move up and down, the start pairing may already differ by two levels
# (the band of the claim), the middle levels branch both ways, and the claim is a two-sided band.
# The cause is a real update-interval difference, not a denial of service.
#
# Domains. kd in [10, 27.5] (constant); k1 in [10, 27.5] (it relaxes to kd: forward invariant);
# k in [14, 42.5] = [10 + 480/120, 27.5 + 1800/120]: every level relaxes k to k1 + r/120 inside it
# (forward invariant on both sides), below the capacity density 45 where the free-flow model holds.
# The right guards partition the domain (no coverage gap); every left mode has a satisfiable start
# (equal states); the left guards are re-checked at every poll and partition the forward-invariant
# domain, so no run is dropped.
# Letter windows. M and B: at every polling interval above 20 s the covers take ceil(interval / 20)
# design updates per deployed window (budget 2 at 30 and 40 s, 3 at 50 and 60 s) with branching 2 on
# the path; none at 20 s. Claim window at 40 s: the 8 requirement sits in the upper branch
# [7.00, ...) of the certifying set, 1.00 above its lowest point and 3.00 below 11.00, from which an
# arbitrary schedule certifies too (law independence); the isolated point 5.00 is below it.
#
# Verdicts (RELCERT_IMPLIED_CUT=1 unless stated). With the band 8 (measured 2026-10-29): CERTIFIED
# (2.2 s); certifying set {5.00} and [7.00, ...) (swept 2026-10-30); --wellformed and --handoff as
# below. Ablations (band 8, measured 2026-10-30): CERTIFIED under RELCERT_SYNC=1,
# RELCERT_NO_PRUNE=1, RELCERT_NO_CHOICE=1, NO_PRUNE+NO_CHOICE, SYNC+NO_CHOICE, RELCERT_NO_CUT=1,
# RELCERT_NO_IMPLIED_CUT=1, RELCERT_NO_LINEAR_CUT=1, RELCERT_NO_REPO=1, without
# RELCERT_IMPLIED_CUT, RELCERT_OPREGION=1, RELCERT_NO_PAIR_STRETCH=1 and RELCERT_WELLFORMED_STRICT=1
# (4.1 s).
# Cover: every left mode at lambda 1, budget 2, joint steps only; admissible starts span three to five
# levels (the band 8 reaches two bands away); branching 2 at every left mode. Pruned R1440 -> R1800
# (R1440 always raises the density; not load-bearing: NO_PRUNE certifies). Rows identical
# (--handoff 36/36, vacuous). relcert --wellformed:
# R1800 ok (exit->R1440,R1200), R1440 ok (exit->R1200), R1200 ok (exit->R1440,R960), R960 ok
# (exit->R1200,R720), R720 ok (exit->R960), R480 ok (exit->R960,R720), 0 UNKNOWN, 0 BLOCKING.
# Letters: M B.
