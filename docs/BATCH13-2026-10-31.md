# Batch 13, 2026-10-31 (branch `benchmark-fixes`): stretch 0 only within the declared range

Problem: batch 12 made stretch 0 a candidate for every benchmark, which bypassed each file's
DECLARED stretch range `[lambda_min, lambda_max]`, part of its stated timing tolerance (the paper:
the tool tries "grid values in the declared range"). `lit_freedm_meter` declares `[1, 1]` (its
source treats time as public, lock step) yet 8 of its 12 windows used stretch 0 in batch 12.
Standing rules kept: suite exactly 50, one serial `lake build` at a time, commits by explicit
path, no trailers, no hand edits of generated files.

## 1. The rule

* **Stretch 0 is a candidate only when the declared range includes 0**, i.e. `lambda_min = 0`, and
  the run feature is on (`RELCERT_NO_STUTTER=1` stays the ablation switch). New predicate
  `Run.stutterAllowed p := p.stutter && (parseRat p.lambdaMin).getD 1 == 0`
  (`Trusted/Run.lean`). The parser already accepted `lambda_min = 0` (no change).
* **Candidates** (`OracleAPI`, the lambda loop): `lambdaCandidates lmin lmax epsL epsR
  (stutterAllowed p)`. `0` is still the LAST candidate, after every positive stretch, and the
  per-pairing fallback is unchanged (each pairing takes the smallest positive stretch at which it
  passed, `0` only if none). The positive grid is unchanged for every file: `εR/εL` and the
  21-point grid on the declared range with `0` removed. A file with `lambda_min > 0` therefore
  runs exactly the batch-12 search minus the stretch-0 candidate.
* **CLI guard**: a cover with a stretch-0 pairing and `!stutterAllowed p` is an ERROR (was
  `!p.stutter`).
* **Kernel gate**: `Emitted.timeOK` admits `lamN = 0` iff `Run.stutterAllowed p` (was `p.stutter`),
  decided in the kernel on the IR's `lambdaMin` string (as `epsilon` already was). No proof
  changed (the gate's disjunct only feeds `0 ≤ lam`); no `sorry`, no new axiom.
* **Bridge instances**: `gen_bridge.py`'s `stutter_on` now states
  `RelCertifier.Run.stutterAllowed IR = true` (the name kept; it implies the old
  `IR.stutter = true`). Emitted for the files whose cover has a stretch-0 pairing:
  `lit_nahs25_salt_tank` and the demo `salt_tank_stutter` (batch 12: also `lit_freedm_meter` and
  `vehicle_accel_copy`).
* **Kernel negatives** (`scripts/stutter_kernel_checks.lean`): besides the IR with the feature
  off, the IR with the feature on and `lambdaMin := "1.0"` fails `structOK` for both the demo
  and the suite salt tank (still 6 axiom lines, exit 0).
* Pre-landing right-only certificates: unchanged (always on).

## 3. A parser bug behind S-used, and the reposition table

The letters' S-used rule already counted stretch 0 ("a stretch other than 1, 0 included"), yet
batch 12 credited `lit_freedm_meter` with no S although 8 of its windows were at stretch 0. Cause:
`suite_v2_matrix.parse_cover` matches one window per line, and Lean's pretty-printer wraps a
window wider than its line width (`lit_freedm_meter`'s 12 x 12 windows, `lit_csf21_vehicle_bus`),
so those two covers parsed to NO windows: every cover-derived cell and used letter of those files
was empty (S, R, M, B used), a silent pass. Fix: `unwrap_cover` joins every indented line that does
not start a window or the cover header to the previous one (lines at column 0 untouched);
`parse_preland` and `gen_pack_rows.py`'s own strata parser normalize the same way. Validation:
over the 52 cover leaves and the 52 `--emit-cover` outputs every cover that parsed before parses
identically, and the two wrapped ones now parse to all their windows.

Consequence for the reposition quick-check table (`gen_pack_rows.py --dyn`, whose anchor string
was also stale and is fixed): the 122 packs of `lit_csf21_vehicle_bus` (48) and
`lit_freedm_meter` (74) were missing from `dynPacksV2` (their Z3 groups were always sent by the
bridge runner, which reads the records). The table is now 252 packs in 19 benchmarks, 950 groups
(was 130 packs, 610). The joint (modal) table is unchanged (the salt tank's rows reference its
unchanged cover; `lit_freedm_meter` has no modal rows).
